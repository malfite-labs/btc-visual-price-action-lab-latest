## 0. 八项核心原则（不可突破的系统红线）

未来任何新增策略，不仅要能交易，还必须能够被**统一管理、统一研究、统一保护**，并具备**标准化的跟单接口兼容能力**：

1. **优先复用公共接口与动态发现**：新增策略必须优先接入现有公共接口、公共状态机、公共行情门禁和标准化账本契约，实现动态发现与零手工拼装接入。
2. **杜绝按策略逐模块硬编码**：严禁每新增一套策略，就需要分别修改主控制台、策略池、策略研究中心及实盘跟单模块。若现有代码仍有按策略 ID 硬编码的分支，应通过做减法将其抽象为契约识别。
3. **算法独立，对外接口与口径完全统一**：策略内部信号与仓位算法允许完全不同（如声明式单周期规则、多周期共振引擎、缠论结构引擎等），但对外 API 字段、状态码、启停与风控保护、账户/绩效统计口径及跟单成交事件格式必须严格统一。
4. **23 套策略全量回归基线**：每次新增策略或调整接入层，均必须以当前 **23 套策略** 作为完整回归验收对象，确认新策略对齐且既有 23 套策略零回归。
5. **全项门禁未过不得标记为接入完成**：任何新策略未通过本规范第 5 节全部 **13 项强制功能验收** 前，**严禁**宣称「接入完成」「上线完成」或交付给用户。
6. **纸盘上线 ≠ 实盘跟单授权（默认零实盘授权红线）**：新增策略进入纸盘研究后，在 Demo 虚拟盘与正式实盘跟单中必须**默认未选中、未启用**。严禁任何自动开启实盘跟单、自动改杠杆或自动提交真实交易所订单的行为。
7. **保持架构简单，优先做减法**：优先通过消除硬编码列表、复用统一适配器和 Schema 自识别达成标准化；严禁为了“形式上的标准化”而过度重构现有稳定运行的交易引擎与前端架构。
8. **既有策略与实盘零扰动原则**：完善规范或新增策略时，**严禁**修改既有策略的交易逻辑、参数、账户余额、在途持仓、止盈止损保护或正在运行的 Demo/正式实盘跟单配置。

## 1. 两种标准接入模式与动态发现契约

V3.1 正式支持两类策略接入模式；无论采用哪种模式，**对主控制台、策略池、研究中心 V3 和跟单中心暴露的外部契约必须完全一致**。

### 模式 A：声明式策略（推荐首选，`btc-lab-declarative-strategy/v2`）

适用于可用声明式指标/形态 AST 表达的策略（如 `PA-01..PA-08`、`pa-chan-center-divergence`）：

- **零代码接入**：直接通过策略池「添加策略文件」（`POST /api/v1/strategy-pool/upload`）上传合法 UTF-8 JSON，无需修改后端、前端或桌面端任何代码。
- **自动闭环**：
  1. `strategies` 表维护唯一 `id` 与启用状态，`versions` 表按 `(strategy_id, version)` 与 `sha256` 不可变归档完整策略 JSON 文档；`StrategyPool.list()` 自动解析中文 `name`、`description` 与版本列表。
  2. 上传时自动在 `accounts` 表初始化 `$10,000.00 USD_RESEARCH` 独立纸盘账户。
  3. 自动纳入 `COMMON-MARKET-GUARD-V1` 公共行情门禁、15 分钟自然周期调度（`StrategyPool.cycle()`）与实时报价止盈止损巡检（`StrategyPool.monitor_quote()`）。
  4. 自动进入主控制台、策略池（含版本更新与 3 个月历史回测）、策略研究中心 V3（全 8 标签页与报告导出）及 Demo/正式实盘跟单可选列表（默认未启用）。

### 模式 B：独立算法扩展执行器（Extension Engine）

适用于多周期状态机、自定义结构识别等声明式 JSON 无法表达的策略（如 `PA-09`、`PA-10`、`R01..R06` 及未来新增扩展系列）：

扩展执行器内部算法自由，但**必须**遵守以下统一外部契约，以确保无需修改主控制台、策略池 UI、研究中心与跟单引擎：

| 契约维度 | 强制要求 | 自动发现机制（零硬编码） |
|---|---|---|
| **独立账本存储** | 存放在标准扩展目录（`data/pa-v1-extensions/<ID>.sqlite3`、`data/r-series/<ID>.sqlite3` 或 `data/extensions/<ID>.sqlite3`） | `build_live_paper_rows()`、`strategy_source_path()`、`research_v3_engine.py` 按目录自动扫描 |
| **SQLite Schema** | 必须包含 `snapshot(id, value)`（JSON 快照，含 `strategy_id`/`name`/`version`/`config_sha256`/`account`/`position`）与 `fills(id, value)`（幂等 JSON 成交记录，含 `fill_id`/`trade_id`/`effect`/`side`/`direction`/`quantity`/`price`/`occurred_at`/`reason`/`version`） | `scripts/live_copy_v2.py` 的 `paper_fills()` 自动检测 `snapshot` 表并路由至 `pa_ext_fills()`，**零策略 ID 前缀硬编码** |
| **API 注册字段** | 在 `/api/v1/strategy-pool` 返回项中提供标准字段：`id`、`name`、`active_version`、`enabled`、`status`、`last_action`、`account`、`position`、`config_sha256`、`is_extension: true`（或兼容既有 `is_r_series: true`） | 主控制台、策略池与研究中心 V3 统一消费同一 API 契约；策略池对 `is_extension` 自动展示清晰的中文版本/回测说明而非静默报错 |
| **公共行情门禁** | 必须直接调用 `backend/common_guard.py` 的 `evaluate_common_market_guard()` | 与全系统 23 套策略共享同一断联阻断与新鲜报价自动恢复语义 |
| **统一退出保护** | 必须接入共享实时报价巡检；用户暂停策略仅阻止新开仓，绝不中断在途持仓的止损/止盈退出 | 保证极端行情与人工暂停下的仓位安全 |
| **历史回测归档** | 若包含独立研究回测/跨时期验证产物，须归档至独立研究目录并明确标注 `BACKTEST_SAVED`，严禁写入纸盘账本 | 策略研究中心 V3「版本与回测对照」自动读取并严格隔离展示 |

## 2. 统一状态显示与中文语义规范

所有策略（含核心策略、镜像策略、声明式池策略及扩展算法策略）必须严格复用 `COMMON-MARKET-GUARD-V1` 与 `scripts/local_dashboard.py` 的 `pa_status_label()` / `strategy_status_appearance()` 统一状态映射：

| 后端原始状态码 | 统一中文展示 | 视觉色系 | 规则说明 |
|---|---|---|---|
| `RUNNING` / `WAITING_SIGNAL` / `ENABLED` | **运行中** | 绿色 | 策略已启用、行情健康、等待信号或持仓监控中；`last_action='WAIT'` 展示为「等待信号」，原始状态码完整保留供诊断 |
| `MARKET_RECOVERING` / `MARKET_STALE` / `RECOVERING` | **行情恢复中** | 琥珀色 | 公共行情门禁判定断联或报价陈旧，自动阻断新开仓；行情新鲜后自动恢复，绝不补开过期信号 |
| `RECONCILING` | **对账中** | 琥珀色 | 启动或断联恢复后的只读账本/持仓核对中 |
| `RECONCILE_ERROR` / `ERROR` / `PROTECTED` | **对账异常** | 红色 | 存在需要人工关注的异常，绝不允许掩盖或伪装为「运行中」 |
| `PAUSED` | **已暂停** | 灰色 | 用户手动暂停新开仓；在途持仓的止损/止盈退出保护持续生效 |
| `DISABLED` / `STOPPED` | **已停用** | 灰色 | 策略未启用 |

> **严禁**在主控制台、策略池或研究中心界面直接裸露 `WAITING_SIGNAL` 等英文原始状态码，也严禁为了美观而将异常/恢复态伪装为绿色「运行中」。

## 3. 声明式策略文件格式与版本更新保护（模式 A）

### 3.1 文件格式与必要字段

策略文件必须为 UTF-8 编码 JSON（单文件 ≤ 64 KB），`format` 固定为 `"btc-lab-declarative-strategy/v2"`：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `format` | string | 是 | 固定 `"btc-lab-declarative-strategy/v2"` |
| `strategy_id` | string | 是 | 全局唯一 ID（小写字母/数字/连字符，如 `pa-chan-center-divergence`）；**严禁通过修改 ID 实现改名** |
| `name` | string | 是 | 面向用户的中文名称；缺失时回退为 `名称待完善（<id>）` |
| `version` | string | 是 | 语义化版本号（如 `"1.0.0"`、`"1.1.0"`）；同一策略版本号不可覆盖 |
| `description` | string | 建议 | 策略核心逻辑与适用行情说明 |
| `market` | string | 是 | 固定 `"BTC/USD"`（映射 Binance USDⓈ-M BTCUSDT 公开行情） |
| `timeframe` | string | 是 | 固定 `"15m"` |
| `parameters` | object | 是 | 规则中引用的全部可调参数字典 |
| `entry` | object | 是 | 包含 `long` 与 `short` 两个声明式 AST 表达式节点 |
| `position` | object | 是 | 含 `direction`、`entry_timing`（`next_open`）、`max_hold_bars`、`same_bar_priority`（`stop`）、`stop` 与 `target_r` |
| `risk` | object | 是 | 固定 `currency: "USD_RESEARCH"`、`initial_equity: "10000"`、`max_leverage: 5`、`risk_fraction: "0.02"` |

### 3.2 版本更新与持仓保护规则

1. **绑定式更新**：在策略池中**右键目标策略行 →「更新策略（上传新版本）」**，自动锁定 `expected_strategy_id`。
2. **强校验阻断**：`strategy_id` 不一致、版本号重复、SHA-256 重复或规则非法时直接拒绝，原运行版本不受影响。
3. **持仓与账本保护**：更新版本绝不重置账户、历史权益、历史成交或跟单映射；在途持仓严格沿用其开仓时记录的 `position.version` 与原止盈止损规则，新版本仅对平仓后的新开仓生效。

### 3.3 历史回测规范

- 所有合规声明式策略自动支持日历日期选择（北京时间 UTC+8，内部对齐 15m UTC 边界，最大跨度 **3 个自然月**，超限明确拒绝不静默截断）。
- 自动预加载指标预热 K 线（不产生起始日期前的成交），自动检测缺口与重复 K 线，结果写入独立 `strategy-pool-backtests.sqlite3`，零污染纸盘与实盘账本。

## 4. 统一跟单接口与实盘安全红线

1. **动态发现与零硬编码适配**：
   - `scripts/local_dashboard.py` 的 `build_live_paper_rows()` 自动汇总核心策略、镜像策略、策略池未归档策略及所有标准扩展目录（`data/pa-v1-extensions/`、`data/r-series/`、`data/extensions/`）的策略 ID 与中文名。
   - `scripts/live_copy_window.py` 的 `strategy_source_path()` 自动定位对应独立 SQLite 账本。
   - `scripts/live_copy_v2.py` 的 `paper_fills()` 对非核心策略自动按 SQLite 表结构（存在 `snapshot` 表 → `pa_ext_fills()`；否则 → `pa_pool_fills()`）解析开多/开空/加仓/部分平仓/全部平仓及保护退出事件，支持幂等游标与去重。
2. **默认零实盘授权红线**：
   - 新策略上线纸盘后，在 Demo 与正式实盘跟单中**默认未选中、未启用**。
   - 未经用户手动在「实盘跟单中心」显式新建配置并确认启用，严禁任何脚本或 AI 工具代为开启 Demo 或正式实盘跟单、修改交易所杠杆或下达订单。

## 十、补充强制验收门禁：G19（系统资源与扩容验收）与 G20（统一策略生命周期验收）

### G19｜系统资源与扩容验收规范（强制）

未来任何新增策略或架构变更，必须自动复用以下公共基础设施，**禁止**为单策略创建独立行情连接、独立常驻进程/线程或重复全量计算公共指标：

1. **G19-1 共享行情与指标复用**：必须通过 `SharedMarketHub` 获取 15m/1h/4h/1d 共享 K 线与共享上下文，高周期/上下文缓存命中率 **≥ 95%**。
2. **G19-2 报价热路径与零溢出**：必须接入 `ActivePositionIndex`（`ProtectionWatchlist`），空仓且无待执行单策略在常规报价到达时必须零 SQLite I/O；正常行情下 `worker_ms_p95 ≤ 15 ms`、`age_ms_p95 ≤ 1000 ms`（严守 2000ms 行情门禁）、`overload_events == 0`。
3. **G19-3 自然周期扇出耗时**：38 套策略 15m 自然收盘扇出 `last_fanout_ms ≤ 500 ms`；100 套真实逻辑压测 ≤ 1,500 ms；200 套压测 ≤ 3,000 ms。
4. **G19-4 查询隔离与缓存**：高频只读接口必须复用 `ReadOnlySnapshotCache`（事件驱动失效 + 版本/时间新鲜度元数据），命中率 **≥ 80%**；回测与研究查询不得阻塞交易与保护线程。
5. **G19-5 自适应 REST 兜底**：WebSocket 健康且报价新鲜（`≤ 1500ms`）时停止高频 REST 轮询；WS 异常或超龄时自动切回 0.8s REST 兜底，严禁陈旧报价覆盖新鲜有效报价。

### G20｜统一策略生命周期验收规范（强制）

全部策略（含 A/B/C/D/E/G、PA、Chan、R、S、AY 及未来新增策略）必须统一接入 `StrategyLifecycleManager`（`data/strategy-lifecycle.sqlite3`）：

1. **G20-1 统一柔和暂停**：暂停仅阻止新开仓，**必须保留已有持仓、实时止盈止损与保护退出**；手动平仓为独立操作，不得与暂停混用。
2. **G20-2 八项删除安全门禁**：删除前必须在策略专属账户锁（`AccountLockRegistry`）保护下全部通过：① 已停止新开仓；② 无持仓；③ 无待开仓/待退出/异常事务；④ 无 Demo 跟单绑定；⑤ 无正式实盘跟单绑定；⑥ 无其他策略依赖（如 C→G 镜像）；⑦ 账本对账正常；⑧ 用户完成策略 ID 二次确认。任何条件不满足必须 HTTP `409` 拦截，禁止自动强平或修改跟单配置。
3. **G20-3 真正释放运行资源**：删除后必须注销调度、清理 `ActivePositionIndex`、释放专属内存缓存与账户锁、安全 checkpoint 并移出独立 SQLite、保留共享行情与公共缓存不受影响。
4. **G20-4 冷归档与重启防复活**：删除前必须生成可读且含 SHA-256 校验的冷归档包（`data/archived-deleted/`），并在 `strategy-lifecycle.sqlite3` 写入墓碑；系统重启后不得自动复活已归档或已删除策略；显式重新注册默认保持禁用且禁止自动实盘跟单。
5. **G20-5 全模块自动同步**：卸载后主控制台（含动态分组数量）、策略池、策略研究中心 V3、实时 K 线、Demo/实盘跟单选择器及 AI 只读 API 必须自动同步。
