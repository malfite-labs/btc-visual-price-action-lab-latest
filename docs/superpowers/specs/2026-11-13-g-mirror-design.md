# G V1.0 C 反向镜像设计

## 意图

在现有 BTC/USD 内部模拟系统中新增独立 G 策略。G 只消费 C 已经提交到账本的成交，并按相反方向、相同 BTC 数量，用同一时刻可用的 Alpaca 报价侧独立模拟成交。它不运行 K 线规则、不调用模型、不使用历史成交补仓。

## 目标与边界

- G 使用独立的 SQLite 账户、镜像映射、审计事件和成交记录；起始权益 `$10,000 USD_RESEARCH`，单笔风险预算 `2%`，最大杠杆 `5x`。
- 每个 C fill 通过稳定的 C fill ID 幂等处理，持久化 C/G 交易和成交映射、报价快照、成交时间与延迟。
- C fill 及 outbox 事件同一 SQLite 事务提交；提交后同步通知 G。G 异常不传播回 C。重启后由 outbox 重放未处理事件，G 数据库以 C fill ID 去重。
- G 不改变 C 的方向、数量、止损、退出决策或成交价格；C 既有开平仓业务保持原样，只增加成交事件快照及提交后监听。
- G 精确复制每次 C fill 数量；数量精度、有效报价、保证金、5x 或 2% 风险任一不满足时拒绝整笔跟单并记录原因，不缩放数量。
- G 的独立紧急止损按 G 自己的实际进场价及 2% 权益风险预算计算，使用同一报价监控和成本模型，不复制 C 止损。G 先于 C 紧急退出后，本 C 交易不再重开镜像。
- G 支持消费部分开仓和部分平仓事件；当前 C Ledger 的生产接口只产生整笔开仓/平仓，故不扩展 C 的交易能力。G 用每次实际 C fill 数量增减自身聚合持仓。
- G 首次激活记录时间边界；只处理此后提交的 C 成交。若 C 当前已有仓位则保持 `WAIT_FOR_C_NEXT_OPEN` 并忽略旧成交。当前只读检查中 C 已空仓，最近交易已正常时间退出。
- 桌面端通过 G 专用只读接口读取账户和成交；显示顺序 ABCDEGPA，G 不进入 PA 分类，PA 仍为8个。G 没有既有启停接口，因此状态开关只读，不新增交易控制。
- 不做历史回测；不修改 C/ABCDE/PA 策略定义、撮合规则、真实交易设置或行情连接。

## 实现路径与权衡

1. **仅进程内回调**：接入轻，但进程在 C fill 提交后崩溃会丢镜像事件，重启也无法核销；不采用。
2. **按15分钟周期轮询 C 状态/成交**：可能漏掉周期间止损，且轮询空仓会误清 G 账；不采用。
3. **C fill 同事务持久化 outbox + 提交后 G 独立账本消费者**：覆盖周期内报价止损，崩溃可重放且幂等；作为实现路径，符合用户指定的成交事件跟随。

## 风险、状态与失败行为

- 开仓使用 G 方向可成交侧：G LONG 用 ask、G SHORT 用 bid；每边按当前 `CostModel` taker 费率和不利滑点，绝不采用 C 成交价替代 G 成交价。
- G stop 依照 2% 当前权益风险预算预留两边成本后反解 stop 距离并向安全侧取整。精度不足以放置有效保护价则拒绝跟单。
- C 关闭已配对仓位时，G 按该 C fill 的成交数量用当前同侧报价减仓/平仓并产生正常盈亏与费用记录。拒单、G 异常退出或映射不一致都保留事件，C 不受影响。
- G 持仓若发生 `MIRROR_RISK_EXIT`，保持配对终态，直到 C 交易关闭只核销、不再重开；未来新 C trade ID 可重新跟随。
- 初始化、持久化或恢复异常时 G 标为 FAULTED/只拒绝 G 跟单，C 周期和保护路径继续运行。所有市场数据仍复用既有 Alpaca WS。

## 验收

临时 SQLite/隔离应用验证 C LONG→G SHORT、C SHORT→G LONG、C close→G close、报价止损同步、重复事件幂等、重启恢复、G 异常隔离、精确数量/成本/2%风险/5x限制以及紧急退出终态。桌面端通过真实后端 GET 接口核验14行、G 账户/状态/详情；不生成生产测试成交。8011 重载前创建数据库/代码备份，核实 C 当前仓位和保护/待处理状态、唯一监听和启动恢复入口；恢复后复核唯一行情连接、ABCDE/PA8及 C 账户。
